Paidly — Application Wiring Overview

Deep assessment · 26 August 2026 · Codebase + blueprint · Confidential internal briefing

Paidly is a business operating system for SMEs (South Africa–first: PayFast, ZAR). It is not an invoicing-only tool. Roughly 70–75% of the intended SaaS architecture is production-wired. The commercial loop works end to end. Remaining value is concentrated in document-model unification, a first-class Payment Intent layer, and a short list of broken or stub surfaces.

2. Product

Positioning in docs/Paidly-Application-Blueprint.md: shift from “invoice app” to financial workflow platform. Competitive edge is unification, not a single PDF:

Document → Payment Intent → Revenue System, plus shared Experience and Payment Intelligence.

Shipped (advanced)

  • Invoices, quotes, payslips (logical document engine, physical tables still split)
  • Clients, catalog/inventory, cash flow, reports
  • Public share tokens + client portal
  • SaaS billing v2 (plans catalog, trials, PayFast ITN, admin override)
  • Affiliates, waitlist, platform admin-v2

Blueprint remaining (~25–30%)

  • Canonical payment_intents (not yet a table)
  • Single persistence for document kinds
  • Observe stream used as Get Paid intelligence, not just logs
  • Experience consistency (PageTemplate + money CTA contract everywhere)
  • Multi-provider payment rails (PayFast still leaks into UI)

6. Session, realtime, sync

This is one of the most heavily engineered parts of the product. Treat it as foundation, not a feature.

Session / connection

  • AuthContext.impl.jsx — single auth owner; profile via useAuth
  • sessionRefreshScheduler — coalesced refresh (visibility, online, heartbeat)
  • ConnectionLifecycleManager — auth, realtime, wake, network signals
  • RuntimeCoordinator — pauses HTTP while AUTH_RECOVERING / RECONNECTING
  • AppRecoveryLock — sleep/wake: auth first, then realtime, then unlock UI

Live + offline

  • Single multiplex Realtime channel: paidlyRealtimeManager
  • JWT rotation: remove + recreate channel (no stale-auth join)
  • SyncEngine + useSyncQueueStore for deferred writes
  • MutationCoordinator + client_operation_id on invoices
  • Logout purges persisted TanStack Query (IDB)
IDRiskStatus
R-01Direct supabase.auth.getSession() bypasses SessionCoordinator (~40 sites). High-risk: connectionHealth, affiliateClient, ActivityNotificationService.Open, medium
R-02Client-domain invalidation always cascades to invoices (correct for names; noisy for other edits).Open, low
R-03Broad ["invoices"] query invalidation still present for legacy hooks.Open, low

7.9 Revenue — SaaS subscriptions & trials 91

This is one of the most complete subsystems.

  • Plans catalog in DB (Starter R50 / Business R150 / Growth R350 + annual). SPA does not set price.
  • POST /api/subscriptions/create|change|cancel; status from verified PayFast ITN only.
  • 7-day server-side trial for org owners created on/after 2026-08-20 UTC. Invited members do not get a trial.
  • Admin PATCH can extend/grant/suspend/cancel and sets admin_override so expiry jobs cannot revert it. Migration 20260820200000_trial_lifecycle_admin_override.sql.
  • Legacy POST /api/payfast/subscription returns 410.
  • Reporting counts only payment_history.payment_status = completed after cutoff — not trials or admin grants.

11. Improvement programme

P0 — User-visible correctness

ItemEvidenceFix
P0 Register recurring edit route Page file exists; missing from index.jsx; createPageUrl capitalizes only first letter → /Edit-recurring-invoice Add /EditRecurringInvoice (+ aliases); change navigate to createPageUrl("EditRecurringInvoice")

P1 — Architecture / product truth

ItemWhy it matters
P1 Choose a documents system of record Either migrate invoice/quote/payslip reads to documents, or fence hub types (leave, claims, contracts) so dual-write cannot diverge. Blueprint still lists single persistence as roadmap.
P1 Add payment_intents Blueprint v1 contract: intent_id, document_ref, amount/currency snapshot, rail, status. Without it, PayFast leaks, multi-rail is hard, sticky payment CTAs stay page-specific.
P1 Server cron for recurring generation Same pattern as expire-trials. Owners should not need to open the app for cycles to fire.
P1 Multi-brand UX or retire the claim Schema is ready; compose picker is not. Positioning currently oversells this.
P1 Vendors / Budgets persistence Map to Supabase or remove routes. Align Vendors with suppliers to avoid two supplier concepts.
P1 Expand document_events on legacy invoices Hub already inserts events. Invoice observe (sent/opened/clicked/paid/reminded) should be one stream for Get Paid.

P2 — Hardening

  • P2 Migrate bursty getSession callers to getStableSession (R-01).
  • P2 Finish queryPolicies keys; drop bare ["invoices"] invalidation (R-03).
  • P2 Enable or delete payment-reminders cron; stop documenting it as scheduled if it is not.
  • P2 Admin system-health real probes; refresh stale admin markdown.
  • P2 Split AuthContext stable vs volatile to cut re-renders on token refresh.
  • P2 Sync queue max-size + failed-job TTL; org_id on jobs for future multi-org replay.

P3 — Cleanup

  • P3 Remove Excel/Base44 leftovers from shell/signup/dashboard.
  • P3 Implement or delete ItemUsageService TODOs.
  • P3 Documents Import; debounce Zustand persist writes; move large collections off localStorage to IDB.
  • P3 Roll PageTemplate remaining list pages; Experience checklist for new screens.

12. Blueprint v1 contract (still open)

From the Application Blueprint “immediate execution order” — none of these five are fully done:

  1. Add payment_intents table.
  2. Integrate intents into document lifecycle (Deliver → Observe → Intent → Settle).
  3. Expand document_events coverage and ingestion (especially for invoices, not only hub docs).
  4. Sticky right panel CTAs driven by intent status (Pay now / Retry / Send reminder) — one contract.
  5. Event- and due-date-driven reminders as a real scheduled job (currently skipped).

Acceptance: invoice settlement only from provider-verified events; no “mark paid” shortcuts that skip the intent.

13. Recommended sequence

  1. Week 0 — P0 fixes. Recurring edit route + send-path unification. User-visible correctness; small PR surface.
  2. Then — documents SoR decision. Written ADR: hub-for-new-types-only vs migrate commercial docs. Do not keep growing both.
  3. Then — payment_intents + webhook reconciliation. Wrap PayFast; keep payments as settlement records.
  4. Then — intelligence crons. Recurring generation + payment-reminders with reminder_settings in DB.
  5. Then — product honesty. Multi-brand UI or drop; Vendors/Budgets map or retire.
  6. Ongoing — runtime hygiene. R-01 / R-03, AuthContext split, Excel leftover removal.
What not to do next. Do not add another document kind, another payment provider, or another admin page until P0 send/recurring bugs are closed and a documents SoR is chosen. The architecture is already ~70% there; more surface area without those decisions increases dual-path debt.
